# Bothy v0.2: design brief

Status: accepted, 2026-10-14. Extends `docs/SPEC.md` (v0.1). Where this brief and the spec disagree, this brief wins and the spec is updated when the work lands.

## 1. Direction

Bothy is a company agent you install in your own cloud. It holds the company's secrets safely, connects to its systems (models, chat, MCP servers, GitHub), works on its repositories, and asks the right people before anything consequential happens. It keeps its own understanding of the company's code and decisions instead of relying on files inside each repository.

v0.2 adds:

| # | Feature | One line |
|---|---|---|
| F1 | Cloud credentials | Amazon Bedrock with the standard AWS credential chain: no API keys on AWS. |
| F2 | OpenAI Responses API | Default for native OpenAI so reasoning models can use tools (in flight). |
| F3 | Refine mode | Opt-in test-time self-correction (breadth + depth), after arXiv:2608.05643. |
| F4 | GitHub and repositories | Connect GitHub once; the agent reads repos, edits in its sandbox and opens PRs, without the token ever entering a box. |
| F5 | Releases and approval flows | Named environments with their own approvers; deploys go through a card that the right people approve, optionally two of them. |
| F6 | Knowledge | Bothy indexes connected repos and keeps its own project notes, outside the repos. |
| F7 | Onboarding and UI | Three-step setup and a calm, plain-language interface. |
| F8 | Cloud deployment | Documented, tested recipes for AWS (ECS on EC2, EKS) and a single VM. |

Security invariants from v0.1 all still hold: no secret in a box, deterministic policy beats model judgment, cards render from structured actions, fail closed, principal isolation.

## 2. F1 Cloud credentials (Amazon Bedrock)

- New provider `type: bedrock` with `region` and an optional `profile`. Models are Bedrock model or inference-profile ids (`us.anthropic.claude-sonnet-4-5-20250929-v1:0`, `global.anthropic...`, `us.amazon.nova-...`).
- Wire: Bedrock Runtime `ConverseStream` (event-stream framing) with tools, images, system blocks, `cachePoint` blocks for prompt caching where the model supports it, reasoning content round trip (`reasoningContent` with signature) for Claude models, usage incl. cache read/write. Hand-write the Converse mapping like the other clients; use the AWS SDK for Go v2 only for what is unsafe to hand-roll: credential resolution (`config.LoadDefaultConfig`), SigV4 signing and event-stream decoding. No implicit SDK retries (the facade owns fallback).
- Credentials: the full default chain (env vars, shared config and credentials files incl. SSO sessions, web identity / IRSA, ECS container credentials, EC2 IMDSv2). Never stored in Bothy, never shown, never in a box. Doctor reports which source resolved (`sso profile x`, `instance role`, `IRSA role`), never the values.
- Egress: AWS endpoints go through `Egress.SystemClient` like every provider. Credential endpoints are the one exception to the metadata block: a dedicated credentials-only dialer may reach exactly `169.254.169.254:80` and `[fd00:ec2::254]:80` (IMDSv2, PUT token first) and `169.254.170.2:80` or the `AWS_CONTAINER_CREDENTIALS_FULL_URI` host when the SDK asks for container credentials. Boxes, tools, `web_fetch` and MCP never get this dialer; a test proves a box cannot reach metadata.
- Containers: compose documents two modes: on a cloud host the role works with no config; on a laptop, mount `~/.aws` read-only into the gateway and set `AWS_PROFILE`. The setup wizard offers Bedrock when it detects AWS credentials ("Use this server's AWS access").
- Probe lists the account's usable Claude/Nova models (`ListInferenceProfiles` + `ListFoundationModels`) so the user picks from a menu instead of typing ids.

## 3. F3 Refine mode

Paper: N independent drafts (breadth), then D rounds per draft of continue → critique → correct (depth), then a plurality vote over normalized final answers. Verifier-free, no training.

- Off by default. Toggle per message in the composer ("Refine"), per session, and a default in Settings → Models. Config `agent.refine: {enabled: false, drafts: 3, depth: 2, early_stop: true, critic_slot: main}`; paper defaults N=8, D=4 are allowed but the UI shows the cost multiplier before sending.
- Applies to the answer step only: when the model would finish the turn with text (no tool calls), the runner re-runs that final step through refinement with the same context. Tool-calling steps are never multiplied. Drafts run in parallel; continue/critique/correct use role prompts (`internal/agent/refine/*.md`, embedded) written for general tasks: the critic must be able to confirm a draft; the corrector returns a full revised answer ending with a `Final answer:` line.
- Aggregation: extract the text after the last `Final answer:` line, normalize (trim, collapse whitespace, strip LaTeX spacing tokens and one brace layer, drop trailing decimal zeros, lowercase), plurality vote ignoring empty extractions; tie → the earliest draft. The shown reply is the full winning draft. `early_stop`: stop deepening when every draft's normalized answer agrees after a round.
- Honest cost: every internal call is metered and counted against budgets; the run trace shows drafts, critiques, corrections and the vote (collapsed by default). Budgets stop refinement before the run's limits are hit and fall back to the best answer so far.
- Small-model friendly: works with 16K windows by refining only the final step and summarising drafts that would not fit.

## 4. F4 GitHub and repositories

- Connect once in Settings → Connections → GitHub: a fine-grained personal access token or a GitHub App (app id + private key, installation tokens minted on demand). Stored in the vault, used only by the gateway through `Egress.SystemClient` (`api.github.com`, `codeload.github.com`, GitHub Enterprise base URL if configured). Per-repo allowlist chosen at connect time.
- Tools (gateway-side; the token never enters a box):
  - `repo_list` (read): connected repos.
  - `repo_checkout` (local_write): downloads the tarball for a ref into `/workspace/repos/<owner>/<repo>` (os.Root, size and file-count caps, symlinks dropped) and writes a manifest (ref, commit sha, file hashes). Boxes then work on plain files; the box image's git may be used locally without credentials.
  - `repo_changes` (read): diff of the workspace copy against the manifest.
  - `repo_open_pr` (external_send, always a card): creates a branch, one commit (Git Data API: blobs, tree, commit, ref) from the changed files and a PR. The card shows repo, base → head branch, title and the full diff. First contact per repo applies.
  - `github_issues`, `github_pr` (read), `github_comment` (external_send), `github_runs` (read: workflow runs and their status).
- Content from repos, issues and PRs is untrusted (anyone may have authored it): results carry `TaintUntrusted` and are spotlighted, so the trifecta guard applies.
- Schema: `repos` table (connection, owner/name, default branch, allowed, last indexed sha) in a new migration.

## 5. F5 Releases and approval flows

- Config `releases.environments: [{name: staging, repo: owner/name, workflow: deploy.yml, ref_pattern: "main", inputs: {...}, approvers: [user ids or roles], required: 1}]`. `required: 2` means two different approvers, neither of them the person who asked.
- Tool `release_deploy {environment, ref}` (irreversible, never auto, never via rules or grants): dispatches the workflow (`workflow_dispatch`) after approval, then follows the run and posts the outcome back to the originating chat and the web UI. `release_status` (read).
- Approvals gain multi-approver support: an approval can need k distinct approvers from a set; votes are stored (new table `approval_votes`), each vote is audited, the requester's own vote does not count, a single deny resolves it as denied. Cards show "1 of 2 approvals". Chat cards route to every eligible approver's DM.
- Schedules may not deploy (F3 floor extends to `release_deploy`).

## 6. F6 Knowledge

- Index connected repos on checkout and on demand: text files under size caps (skip binaries, vendored and generated paths, `.gitignore`d patterns), chunked by headings / top-level declarations with line ranges, stored in SQLite FTS5 (`knowledge_chunks`, keyed by repo + sha + path + line range). Pure Go, no external service. Optional embeddings stay P2.
- Tool `knowledge_search {query, repo?}` returns ranked snippets with citations `owner/repo@sha:path#L10-L42`; untrusted taint as in F4.
- Project notes: per repo, Bothy keeps its own notes (`<data>/knowledge/<owner>/<repo>/NOTES.md`): what the project is, how it is built and tested, conventions, important decisions. Drafted automatically after the first index by a cheap-model run reading the README, build files and top-level layout; updated when the agent learns something (via a `notes` tool that proposes edits; untrusted-derived edits need approval like tainted memory). Shown and editable in the UI under Knowledge. A session that touches a repo gets that repo's notes summary in its turn-context (byte budget, cache-stable placement).
- Bothy never writes memory files into the repos themselves.

## 7. F7 Onboarding and UI principles

The person using Bothy wants to get work done, not to operate an AI system. The UI should feel like a quiet, well-made tool.

- **Three setup steps:** 1. your account; 2. connect a model (detected options first: "Use this server's AWS access", "Ollama on this computer"; then a provider list with one key field and an automatic check); 3. done, with optional next steps (connect a chat app, connect GitHub, invite people) that can be skipped. Safety preset, spend cap and timezone get sensible defaults and live in Settings.
- **Plain language:** no token counts, context windows, micro-dollars, model ids or config keys in the main flow. Say "This will cost about $0.03" rather than token math; "Bothy wants to run a command" rather than tool names. Technical detail is available behind a "Details" disclosure or in Settings → Advanced.
- **Visual:** one neutral palette with a single accent, system font stack, 4/8px spacing scale, generous whitespace, consistent controls, no gradients, glows, emoji, decorative icons or badge clutter, no card-inside-card. Dark and light themes both first-class. Motion only where it explains a change.
- **Fewer, clearer places:** Chat (with a quiet approvals inbox), Knowledge, Activity (runs, schedules, usage), Settings grouped as General, Models, Connections (chat apps, GitHub, MCP servers), People, Security (approvals, sandbox, vault), Advanced.
- **Empty and error states** say what happened and what to do next, in one sentence, with one primary action.
- Accessibility stays a requirement: keyboard-only approval flow, focus management, contrast AA, 360px layouts.

## 8. F8 Cloud deployment

`docs/deploy/` with tested recipes: a single VM with compose (any cloud), AWS ECS on EC2 (gateway + sandboxd, task role for Bedrock), and EKS (IRSA; sandboxd needs a node with a container runtime socket or falls back to no-sandbox mode with the banner). Fargate is documented as single-container mode (no sandbox). Each recipe states how secrets are held (vault + KEK from the platform's secret store) and how to reach the UI privately.
